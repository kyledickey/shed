## How it works

A 1Password Environment is a named set of environment variables kept in 1Password. A service can link one Environment by its ID, together with the token of a service account that can read it. When the service deploys, shed reads the Environment with that token and adds its variables to the deployment's environment, between the variables shed injects and the service's own variables.

shed only reads. It never writes to 1Password, and the dashboard and API never show a token again once it is saved. Each token is stored encrypted in shed.db, on the service's link.

The Variables tab of a linked service lists the Environment's variables under the service's own, read live from 1Password and marked with the 1Password logo. They can be revealed and copied but not edited there. A key the service also defines is listed once, as the service's own variable, marked "overrides 1Password".

## Setup

1. In the 1Password app, open **Developer > Environments** and create an Environment, or pick an existing one. Add the variables the service needs.
2. Open the Environment, choose **Manage environment > Copy environment ID**, and keep the ID for step 4.
3. On 1Password.com, create a [service account](https://developer.1password.com/docs/service-accounts/) with read access to just this Environment, and copy its token. The grant must name the Environment explicitly: access to the vault it lives in is not enough, and reads fail with 403.
4. In shed, open the service's **Variables** tab, click **1Password**, paste the Environment ID and the service account token, and click **Link**. shed reads the Environment once with the token before saving; if that fails, the dialog shows 1Password's error and nothing is saved.
5. Deploy the service.

1Password fixes a service account's access when the account is created: you can't grant it another Environment later. So use one service account per Environment, which also keeps each token able to read only the secrets of the service that holds it. Linking another service to a new Environment means creating a new service account for it.

The same dialog changes the Environment ID, replaces the token, or unlinks the Environment. Leave the token blank to keep the saved one; shed still checks it against the Environment ID before saving. Unlinking forgets the token.

Over the API, linking is `PUT /api/services/{id}/onepassword` with `{"environment": "<id>", "token": "ops_…"}` (omit `token` to keep the saved one), and unlinking is `DELETE /api/services/{id}/onepassword`. Both return the service, whose `onePassword` field says which Environment is linked and whether a token is saved, never the token itself.

## Precedence

Each service's variables are layered, later winning:

| Layer                            | Example                       |
| -------------------------------- | ----------------------------- |
| Injected by shed                 | `PORT`, `SHED_PRIVATE_DOMAIN` |
| The linked 1Password Environment | `STRIPE_SECRET_KEY`           |
| The service's own variables      | `DATABASE_URL`                |

So a shed variable with the same key as a 1Password one replaces it, and a 1Password variable named `PORT` replaces the injected one.

[References](/docs/variables#references) see the same layers. `${{ STRIPE_SECRET_KEY }}` in one of the service's own values reaches the 1Password key, and `${{ api.STRIPE_SECRET_KEY }}` from another service reaches the 1Password key of `api`'s Environment. Another service's Environment is read only when a reference looks up a key that service doesn't define itself.

## When 1Password is read

shed reads an Environment only when something needs its values right then:

- **A deployment starts**, including redeploys and rollbacks. Each Environment involved is read at most once per deployment.
- **The Variables tab is open** on a linked service. The dashboard keeps the list for a minute before reading again.
- **A resolved value is requested**: copying a variable that contains a reference, or `GET /api/services/{id}/variables/resolved`.
- **An agent calls `list_variables`** over [MCP](/docs/mcp). It returns names only, marked as coming from 1Password.

`GET /api/services/{id}/variables/onepassword` returns the linked Environment's variables, `{}` if none is linked, 409 if the link has no token, and 502 if the read fails.

Restarts, crash recovery, starting a stopped service, and shed's own boot never read 1Password. They reuse the environment recorded on the active deployment.

## Applying changes

1Password has no change notifications that shed can subscribe to. Its Events API is an audit feed for Business accounts that has to be polled, and shed doesn't use it. A change in 1Password, whether a new key, an edited value, or a rotated secret, reaches the service on its next deployment. Redeploy after you change a value.

Linking, relinking, and unlinking also apply on the next deployment, like every other [setting](/docs/concepts#when-settings-apply).

## Failures

A read that fails fails the deployment, with the 1Password error in the build log and on the deployment. Common causes are a token that was revoked or expired, a service account without access to the Environment (403), a rate limit, and a network error. The running deployment keeps serving: a failed read happens before the new container starts.

A link without a token fails every deploy of its service with "1Password link of service … has no token; add one on its Variables tab". Links made by earlier versions of shed, when one token in Settings served every service, are in this state after upgrading: the old token is deleted, not copied, so that each link gets a service account of its own. The Variables tab shows **Add token** on such a link. Running containers keep their variables.

## Limits

- **Read-only.** shed never creates, edits, or deletes anything in 1Password.
- **Beta.** Programmatic access to Environments is a 1Password beta, so its behavior may change.
- **Rate limits.** Service accounts are rate limited by 1Password. Each deploy reads each involved Environment once, and so does each refresh of the Variables tab and each `list_variables` call. The hourly limit applies to each token, so to each service account; the daily limit is shared by every service account in the 1Password account.

| Account                 | Per token, hourly | Per account, daily |
| ----------------------- | ----------------- | ------------------ |
| Business                | 10,000 reads      | 50,000 reads       |
| Teams                   | 1,000 reads       | 5,000 reads        |
| Families and individual | 1,000 reads       | 1,000 reads        |

- **Memory.** 1Password's client runs inside shed and uses about 110 MB of memory once loaded. It loads in the background when shed starts and a link has a token, or on the first read. Unlinking every Environment doesn't free it; the memory is freed on shed's next restart.

## Masking

Every value that came from 1Password is masked as `***` in build and runtime logs, the same way as the service's own variables. See [secret redaction](/docs/logs#secret-redaction) for the limits of masking.
