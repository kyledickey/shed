## What it runs

Telemetry is off until you turn it on under **Server, Telemetry**. Then shed runs four containers, each on the host network, listening on loopback only, with a pinned image and a named volume for its data:

| Component       | Container                | Listens on (config key)                   | Volume                   |
| --------------- | ------------------------ | ----------------------------------------- | ------------------------ |
| VictoriaMetrics | `shed-telemetry-metrics` | `telemetry.metrics_addr` (127.0.0.1:8428) | `shed-telemetry-metrics` |
| VictoriaLogs    | `shed-telemetry-logs`    | `telemetry.logs_addr` (127.0.0.1:9428)    | `shed-telemetry-logs`    |
| VictoriaTraces  | `shed-telemetry-traces`  | `telemetry.traces_addr` (127.0.0.1:10428) | `shed-telemetry-traces`  |
| Grafana         | `shed-telemetry-grafana` | `telemetry.grafana_addr` (127.0.0.1:3001) | `shed-telemetry-grafana` |

Loopback keeps them unreachable from the internet and from your services' containers. Change the addresses under [`[telemetry]`](/docs/configuration#telemetry-addresses) only if a port is taken. Grafana's provisioning files live in `<data.dir>/telemetry/grafana/provisioning`, and VictoriaMetrics' scrape config in `<data.dir>/telemetry/scrape/scrape.yaml`. Both are mounted read-only.

Every container carries the label `shed.telemetry=<component>`, and `shed.spec` holds a hash of its configuration. shed compares that hash on boot and after every settings change, and recreates a container only when its configuration changed. The volume stays.

## Turning it on

Flip **Collect telemetry**. The switch saves at once and shed brings the stack up in the background:

1. Pull each image the first time.
2. Start the three stores and wait for each one's `/health`.
3. Write Grafana's data sources, start Grafana, and wait for it. The first start installs the VictoriaMetrics and VictoriaLogs data source plugins, which needs network access to grafana.com.
4. Create the `shed` folder in Grafana and load the default alert rules into it.
5. Create the folders and default dashboards (see [Folders and dashboards](#folders-and-dashboards)).

Components show **Starting** until they answer their health check, then **Running**. A step that fails shows **Failed** with the error, and shed tries again a minute later. **Restart** on a component restarts its container.

Turning telemetry off stops the four containers and keeps their volumes, so turning it on again resumes with all history and anything edited in Grafana. Both are recorded in the [audit log](/docs/audit) as `telemetry.enable` and `telemetry.disable`.

## Signing in to Grafana

Grafana is at `<server.url>/grafana/`, behind the dashboard's sign-in. Use **Open Grafana** on the Telemetry page or in the top bar. There is no separate Grafana login:

- A signed-out page load goes through GitHub sign-in and comes back to the Grafana page. Other signed-out requests get a 401.
- shed tells Grafana who you are. Grafana creates a user for your GitHub login the first time, with the Admin role. Every allowed user can do everything in shed, so every one is a Grafana admin too.
- Requests that change something must come from the dashboard's own origin, like the API's. Grafana Live's WebSocket must too.
- shed's session cookie never reaches Grafana.

Data sources are provisioned from files: `shed-metrics`, `shed-logs`, and `shed-traces`. Grafana puts them back on every start, so edits to them don't last. Provisioned alert rules can't be edited either; copy one to change it. shed's own API calls sign in as the `shed` admin, whose random password is kept encrypted in `shed.db`.

## Folders and dashboards

While telemetry is on, shed keeps a folder in Grafana for itself, each project, and each service, and fills them with default dashboards:

| Folder                    | Holds                                                                                                      |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| shed                      | Overview, Deploys, API & MCP, Proxy, Host & Docker, Backups, Runtime, Telemetry, Security; the alert rules |
| `<project>`               | the project's Overview, one row per service                                                                |
| `<project>` / `<service>` | Overview and Logs; HTTP and Traces for apps; Postgres, MySQL, MongoDB, or Redis for databases              |
| Archived                  | folders of deleted services and projects                                                                   |

shed reconciles them when telemetry turns on, at boot, when a project or service is created, renamed, or deleted, and every 10 minutes. Folder titles follow renames; dashboard titles never carry a name, so links stay put. A deleted service's folder moves under **Archived** as `<project> / <service> (deleted <date>)`, a deleted project's as `<project> (deleted <date>)`, with its dashboards. Their data ages out with retention.

The project page links to its folder with **Open in Grafana**. A service's **Metrics** tab lists its dashboards and links to its folder, and each deployment links to the service's Overview around the time it ran.

### Editing dashboards

Edit and save any dashboard in Grafana. shed remembers the version it last wrote; once a user saves a dashboard it is **customized**, and shed never overwrites it again. A shed upgrade that changes a default updates only the dashboards nobody customized. On customized ones the service page shows **Newer default available**, and **Reset to default** replaces your version with the current default (recorded as `telemetry.dashboard.reset`).

A dashboard you delete stays deleted. **Restore default dashboards** on the Telemetry page brings back every default that is missing, and leaves the others alone (recorded as `telemetry.dashboards.restore`). New dashboards you create in shed's folders are yours; shed doesn't touch them.

### Annotations

Deploys starting (or a redeploy), going active, and failing, restarts, stops, backups, and restores are marked on the dashboards as annotations. Each is tagged `shed`, its kind (`deploy.started`, `redeploy`, `deploy.active`, `deploy.failed`, `restart`, `stop`, `backup`, `backup.failed`, `restore`, `restore.failed`), `service:<service ID>`, and `project:<project ID>`. Service dashboards show their service's, project dashboards their project's, and shed's own dashboards all of them. To show them on a dashboard of your own, add a Grafana annotation query filtered by those tags. Annotations are written only while telemetry is on, and one that Grafana refuses is dropped.

### Alerts

The default alert rules live in the shed folder: a service restarted more than 3 times in 10 minutes, an OOM kill, host disk above 85%, host memory above 90% for 10 minutes, a 5xx ratio above 5% for 5 minutes at more than 1 request a second, p95 latency above 2 seconds for 10 minutes, database connections above 80% of the maximum, a failed deploy or backup, and telemetry dropping records. No contact point is configured; add one in Grafana to get notified. Firing alerts show on the Telemetry page, and alerts about a service (by its `shed_service_id` label) also on that service's Metrics tab.

## Retention and disk

| Setting                  | Default | Range          |
| ------------------------ | ------- | -------------- |
| Keep metrics for         | 30 days | 1 to 3650 days |
| Keep logs for            | 14 days | 1 to 3650 days |
| Keep traces for          | 14 days | 1 to 3650 days |
| Disk for logs and traces | 20 GB   | at least 1 GB  |

The disk limit is split 60% for logs and 40% for traces; when either share is full, its oldest data is deleted first. Metrics have no disk limit of their own. They are bounded by retention, and VictoriaMetrics stops accepting writes rather than let the disk fall below [`build.min_free_mb`](/docs/configuration#build-limits).

Changing a retention or the disk limit recreates that store's container on the same volume. Its data is kept. The Telemetry page shows each store's disk use, as the store reports it.

The default per-service limits are saved with the other settings; see [Caps](#caps).

## Sending telemetry from your app

While telemetry is on, shed is an OpenTelemetry gateway for your services. Each app's next deployment gets these variables:

| Variable                      | Value                                   |
| ----------------------------- | --------------------------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://shed.internal:4318`             |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf`                         |
| `OTEL_SERVICE_NAME`           | the service name                        |
| `OTEL_RESOURCE_ATTRIBUTES`    | `service.version=<commit SHA or image>` |

Any OpenTelemetry SDK reads them, so instrumenting the code is the only change. A variable you set yourself with the same name wins. They are listed as injected on the Variables tab. Every service's container, databases included, also gets the host name `shed.internal`, pointing at its project network's gateway address on the host. The port is [`telemetry.otlp_port`](/docs/configuration#telemetry-addresses) (4318).

The gateway takes OTLP over HTTP: `POST /v1/traces`, `/v1/metrics`, and `/v1/logs`, protobuf or JSON, optionally gzip, up to 8 MiB a request. There is no gRPC endpoint, and it is not reachable from the internet. It knows the sender by the container's address on its project network, so it labels every record with the service, project, and deployment, whatever the SDK claims; a sender shed doesn't know gets a 403. String attributes, span status messages, and log bodies are masked with the values of every variable in the project and those the container started with. Traces go to VictoriaTraces, metrics to VictoriaMetrics, and logs to VictoriaLogs.

Variables and the host entry are part of a container's configuration, so turning telemetry on or off reaches a service with its next deployment.

## Firewall

Containers reach the gateway on the host's address on their bridge. A host firewall whose default input policy drops packets (ufw's default, firewalld's public zone) would drop these too, so while telemetry is on shed adds one iptables rule per project network that accepts TCP to port 4318 from that network's bridge only:

```sh
-A INPUT -i br-1a2b3c4d5e6f -p tcp -m tcp --dport 4318 -m comment --comment shed-telemetry -j ACCEPT
```

The rules sit at the top of the `INPUT` chain, follow project networks as they come and go, and are removed when telemetry is turned off. shed only changes rules carrying the `shed-telemetry` comment. List them with `sudo iptables -S INPUT | grep shed-telemetry`.

If `iptables` is not installed, shed logs a warning and you need to allow the port yourself, for example `sudo nft add rule inet filter input iifname "br-*" tcp dport 4318 accept`. The gateway only listens on loopback and on the gateways of shed's project networks, so the port is not exposed to the internet either way.

## Container logs

While telemetry is on, shed also ships the output of every service container to VictoriaLogs, with no change to the app. Each line keeps Docker's timestamp and its stream (`stdout` or `stderr`). A line that is a JSON object keeps its top-level fields (up to 64); `msg` or `message` becomes the message, `level`, `severity`, or `lvl` the level, and `trace_id` links to the trace. Other lines take their level from a leading `ERROR`, `WARN`, `INFO`, or `DEBUG`. Lines are cut at 16 KiB and masked like the runtime logs on the Logs tab.

shed remembers how far it shipped each container, so after a restart of shed it carries on where it stopped. Lines that Docker rotated away meanwhile (10 MB times 3 files per container) are lost.

## Caps

Each service may send at most so many spans and log records a second, and so many distinct metric series an hour:

| Cap         | Default | Counts                                                   |
| ----------- | ------- | -------------------------------------------------------- |
| Spans       | 5000/s  | trace spans sent to the gateway                          |
| Log records | 2000/s  | OTLP log records and lines of container output, together |
| Series      | 50000   | distinct metric name and attribute sets in the last hour |

Records over a cap are dropped. The SDK is told how many with an OTLP partial success, so it doesn't retry them. Change the defaults on the Telemetry page, or give one service its own caps in its **Settings, Telemetry** card; either applies within seconds, and a service's own caps are recorded as `telemetry.caps.update`. The same card shows **Dropping telemetry** while records of the service were dropped in the last five minutes. The Telemetry page counts drops by reason over the last hour.

## Resource use

| Component       | Memory  | CPUs |
| --------------- | ------- | ---- |
| VictoriaMetrics | 512 MiB | 1    |
| VictoriaLogs    | 512 MiB | 1    |
| VictoriaTraces  | 384 MiB | 1    |
| Grafana         | 512 MiB | 0.5  |

These are caps, not reservations. An idle stack uses far less, apart from Grafana, which sits near 300 MiB. Plan for up to about 2 GB of memory with telemetry on. The Telemetry page shows each container's CPU and memory against its cap.

## Deleting data

**Delete telemetry data** is only available while telemetry is off. It removes the four containers, their volumes, and `<data.dir>/telemetry`: every stored metric, log record, and trace, and Grafana's users, dashboards, and settings, along with shed's record of which dashboards were customized. It can't be undone, and it is recorded as `telemetry.data.delete`. Turning telemetry on afterwards starts from empty.
